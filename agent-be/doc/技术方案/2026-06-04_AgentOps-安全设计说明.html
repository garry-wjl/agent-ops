01安全总体设计

garry AgentOps 后端 rd-agent-be 是 Agent Sphere 的 Control Plane（控制面），承担会话层、调度层（权限/限流）与数据管理层三大职责。本服务自身不执行 Agent，所有 Agent 调用透传到 rd-points-sphere（Data Plane）。其安全设计遵循纵深防御（Defense in Depth）原则，在请求从浏览器进入、穿过六层架构、落到数据库与对象存储的全链路上分层设防。

1.1 三个访问平面

平面调用方向认证机制说明
Admin 平面前端 rd-agent-fe → beGCAC OAuth (SSO) → 本地 JWT → HttpOnly Cookie用户人机交互主入口
Internal 平面业务平台 platform → be 的 /admin/api/v1/internal/*共享密钥 X-Service-Token + 内网信任拉取 active prompt 等服务间调用
Data Planebe → rd-points-sphereK8s NetworkPolicy 网络层管控（MVP 阶段无应用级鉴权）透传 Agent 执行请求

1.2 安全分层模型

一次受保护的业务请求会依次穿过以下安全关卡，任何一层不通过即在该层终止并返回标准错误码：

┌──────────────────────────────────────────────────────────────┐ │ 浏览器 ── HTTPS ──▶ Cookie: session_token (HttpOnly/Secure) │ └───────────────────────────────┬──────────────────────────────┘ ▼ ┌──────────────────────────────────────────────────────────────┐ │ ① CorsConfig 跨域白名单校验（显式 origin，禁用 *） │ │ ② JwtAuthenticationFilter 解析 JWT → RBAC 路径鉴权 → 注入身份 │ │ ③ UserContextFilter traceId 初始化 + Header 兜底身份注入 │ │ ④ WorkspaceContextInterceptor 工作空间成员校验（403 拦截） │ └───────────────────────────────┬──────────────────────────────┘ ▼ ┌──────────────────────────────────────────────────────────────┐ │ ⑤ Controller @Valid 入参校验 → BaseController 取 ThreadLocal │ │ ⑥ Application 跨空间归属二次校验 + 出参脱敏 + 审计字段写入 │ │ ⑦ Infra/MyBatis-Plus 参数化查询（防注入）+ 逻辑删除 + 隔离过滤 │ └───────────────────────────────┬──────────────────────────────┘ ▼ MySQL (schema 物理隔离 rd_agent) + OSS (预签名 URL)

02认证：GCAC SSO 登录 已实现

平台不自建账号体系，统一接入garry GCAC（gcac.garrycorp.com）SSO，采用标准 OAuth2 Authorization Code Flow。登录全程由三个端点构成，落在 adapter 层 AuthController.java。

端点方法职责
/api/login_gcac/redirectGET生成 state → 302 跳转 GCAC 授权页
/api/login_gcac/callbackGET校验 state → code 换 token → token 换 profile → upsert 用户 → 签发本地 JWT
/api/login_gcac/logoutGET清 Cookie → 302 跳转 GCAC 单点登出
CASE 2-1　OAuth State 防重放（CSRF 防护）

登录回调最常见的攻击是重放 / CSRF：攻击者诱导用户携带伪造的 code 完成回调。我们用一次性 state 令牌防御——授权阶段生成、回调阶段原子消费，无法二次使用。

infra/auth/state/OAuthStateStore.java

// 生成：24 字节 SecureRandom，Base64URL 编码，落 Redis，TTL 600s
public String issue(Duration ttl) {
    byte[] bytes = new byte[24];
    RNG.nextBytes(bytes);                       // SecureRandom，密码学安全随机
    String state = Base64.getUrlEncoder().withoutPadding().encodeToString(bytes);
    redisson.getBucket("gcac:state:" + state).set("1", ttl);
    return state;
}

// 消费：原子删除，命中返回 true 并立即失效（一次性令牌）
public boolean consume(String state) {
    return redisson.getBucket("gcac:state:" + state).delete();
}

回调入口先做 consume(state)，未命中（已用过 / 过期 / 伪造）直接拒绝，从根上阻断重放。明确否定了历史实现里"固定 state 字符串"的做法。

CASE 2-2　client_secret 不出现在 URL

code 换 token 时使用 form-body POST 传递 client_secret（Hutool HttpRequest），而非拼到 query string，避免密钥落入网关访问日志、浏览器历史。client_secret 通过 K8s Secret 注入，配置项 gcac.client-secret 默认值为空，强制生产环境显式注入。

03会话：JWT + HttpOnly Cookie 已实现

登录成功后签发本地 JWT 作为会话凭证，写入 HttpOnly Cookie。算法 HS256（HMAC-SHA256），密钥要求 ≥32 字节 UTF-8（与同 SSO 域 Java/Go 服务共享，便于跨语言互通）。Claims 仅含 uuid / account / roles 三个字段，默认 24 小时过期。

CASE 3-1　Cookie 三重安全属性抵御 XSS / 嗅探 / CSRF

adapter/auth/AuthController.java · infra/auth/token/JwtProperties.java

ResponseCookie.from(jwtProps.getCookieName(), jwt)   // session_token
    .httpOnly(true)                 // ① JS 读不到 → 抵御 XSS 盗取会话
    .secure(jwtProps.isCookieSecure())   // ② 仅 HTTPS 传输 → 抵御明文嗅探

04接口鉴权：过滤器链 + RBAC 已实现

每个受保护请求在进入 Controller 前，必须通过 adapter/security/JwtAuthenticationFilter.java（执行顺序 HIGHEST_PRECEDENCE + 5，最优先）。该过滤器是接口鉴权的第一道闸门。

CASE 4-1　五步认证：401 与 403 精确区分 
protected void doFilterInternal(req, resp, chain) {
    String path = req.getRequestURI();

    // 1) 公开路径直通：登录、健康检查、错误页
    if (routeRoleMapping.isPublic(path)) { chain.doFilter(req, resp); return; }

    // 2) 从 Cookie 提取 session_token；缺失 → 401
    String token = extractToken(req);
    if (token == null) { writeError(resp, UNAUTHORIZED, "missing token"); return; }

    // 3) 解析 JWT；失败 → 写审计 + 401
    UserClaims claims;
    try { claims = tokenIssuer.parse(token); }
    catch (BusinessException e) {
        audit.recordAccessDenied(null, path, "invalid_token");
        writeError(resp, UNAUTHORIZED, "invalid token"); return;
    }

    // 4) RBAC：路径所需角色与用户角色取交集；不足 → 写审计 + 403
    if (!routeRoleMapping.allow(path, claims.getRoles())) {
        audit.recordAccessDenied(claims.getAccount(), path, "role_insufficient");
        writeError(resp, FORBIDDEN, "insufficient permissions"); return;
    }

    // 5) 身份注入 ThreadLocal，请求结束 finally 清理
    UserContextHolder.set(UserContext.builder()
        .userId(claims.getAccount()).roles(claims.getRoles()).build());
    try { chain.doFilter(req, resp); } finally { UserContextHolder.clear(); }
}
  • 401 Unauthorized：令牌缺失 / 非法 / 过期——身份不可信。
  • 403 Forbidden：身份可信但角色不足——权限不够。
  • 两类拒绝都落审计日志（含 path、account、原因），可用于非法访问追踪与暴破检测。
CASE 4-2　路径-角色映射表 RouteRoleMapping

adapter/security/RouteRoleMapping.java

采用 Ant 风格路径匹配的集中式映射，避免权限规则散落在各 Controller：

// 公开路径：完全不走 JWT 校验
PUBLIC_PATHS = [ "/api/login_gcac/**", "/actuator/**",
                "/error", "/favicon.ico" ];

// 角色映射：命中则要求角色交集；未登记路径 → 仅要求"已认证"
public boolean allow(String path, List<String> userRoles) {
    for (entry : mappings()) {
        if (MATCHER.match(entry.getKey(), path)) {
            List<String> required = entry.getValue();
            if (required.isEmpty()) return true;          // 任意已认证用户
            return userRoles.stream().anyMatch(required::contains);
        }
    }
    return true;  // 未登记 → 默认仅需已认证（白名单显式收口）
}

角色体系按 PRD 定义为 admin / editor / viewer 三档；AD 账号到角色的映射由 app.auth.role-assignments 配置驱动。

演进项：SECURITY.md 规划的方法级 @RequirePermission(Role.EDITOR) 注解 + AOP 拦截 + ArchUnit 强制（写接口必须显式标注角色，否则编译期 fail）为下一步细化方向；当前以路径映射表统一收口，资源级权限（如"只能改自己创建的 Agent"）列入 v0.2。

兜底过滤器与上下文清理

UserContextFilter.java（顺序 +10，跑在 JWT 之后）负责初始化 X-Trace-Id 链路 ID，并在 JWT 未注入身份时从 X-User-Id Header 兜底（服务间调用 / 本地 dev）。所有上下文（User / Workspace / Trace）均存于 ThreadLocal，在 finally 中强制 clear()，防止线程池复用导致的身份串号泄漏。

05数据隔离：工作空间多租户 已实现

平台以工作空间（Workspace）为数据隔离边界：Agent、Skill 等资产都归属某个工作空间，用户只能访问自己是管理员或成员的空间。隔离通过"拦截器准入 + 应用层归属校验 + 数据库列过滤"三层联合实现，单层失效仍有后续兜底。

CASE 5-1　拦截器准入：非成员 403

adapter/config/WorkspaceContextInterceptor.java

public boolean preHandle(request, response, handler) {
    String workspaceNum = request.getHeader("X-Workspace-Num");
    if (StrUtil.isBlank(workspaceNum)) return true;  // 无空间头，交下游按 num 校验

    String empNo = UserContextHolder.currentUserId();
    if (StrUtil.isBlank(empNo)) throw new BusinessException(UNAUTHORIZED, "未登录");

    // 查调用者在该空间的角色：ADMIN / MEMBER / null（非成员）
    String role = workspaceQueryService.getMyRole(workspaceNum, empNo);
    if (role == null) throw new BusinessException(FORBIDDEN, "无权访问该空间");

    WorkspaceContextHolder.set(WorkspaceContext.builder()
        .workspaceNum(workspaceNum).role(role).member(true).build());
    return true;
}

注册在 /api/v1/workspace/**、/api/v1/agents/**、/api/v1/skill/**，排除 list / create。afterCompletion 中 WorkspaceContextHolder.clear() 防泄漏。

CASE 6-2　SQL 注入防护：全量参数化

持久层统一用 MyBatis-Plus，所有查询走 LambdaQueryWrapper 或注解参数绑定，禁止字符串拼接 SQL（由 ArchUnit 架构守卫机械检查）。参数化预编译从根本上消除 SQL 注入。

同时全表启用逻辑删除（deleted 字段），查询自动过滤 deleted=0，避免物理删除导致的数据不可追溯。

XSS 防护：Prompt / Skill 内容作为纯字符串存储，不做 HTML 渲染（编辑器与调试台均用 textarea 展示），从源头规避存储型 XSS。操作人 ID 等敏感身份字段一律从服务端 ThreadLocal 读取，绝不采信前端入参，防止越权伪造操作者。

07密钥安全：加密存储与脱敏

平台涉及两类敏感密钥：① 业务侧的模型供应商密钥 ConfigSnapshot.modelApiKey；② 对外开放调用的 Agent API Key（ak- 前缀）。两者统一遵循"加密存储、绝不存明文、出参掩码、按需解密"的密钥治理原则（2026-06-04 Agent 优化 v1.1）。加解密能力收敛在 infra/common/security/SecretCipher.java，全局复用。

CASE 7-1　模型密钥 SecretCipher 加密存储 + 出参脱敏

模型密钥 modelApiKey 通过 SecretCipher 加密后落库，数据库中不存明文；运行时在 OpenAiChatModelFactory / ConfigAgentBuilder 中按需解密再调 LLM。面向前端的详情/版本出参再叠加一层掩码，双重保护。

infra/common/security/SecretCipher.java · application/agent/AgentQueryService.java

// ① 写入：加密落库（绝不存明文）
entity.setModelApiKey(secretCipher.encrypt(plainKey));

// ② 运行时：按需解密后调用 LLM
String real = secretCipher.decrypt(entity.getModelApiKey());

// ③ 出参：面向前端再掩码（detail / versionList / 版本详情 三处）
private void maskApiKey(Map<String,Object> snapshot) {
    Object apiKey = snapshot.get("modelApiKey");
    if (apiKey != null && !apiKey.toString().isEmpty()) {
        snapshot.put("modelApiKey", "***");
    }
}

"加密存储 + 出参掩码"形成纵深：即便出参脱敏被绕过，库内仍是密文；即便密文被读取，无密钥不可解。

CASE 7-2　Agent API Key：hash 认证 + cipher 可逆 + prefix 掩码（三件套）

对外开放接口用 Agent 自己签发的 API Key（ak- 前缀）认证。一把 Key 在库内拆成三个派生物，认证、展示、可逆解耦：

domain/agent/AgentApiKey.java · infra/agent/factory/AgentApiKeyFactoryImpl.java

字段算法用途
key_hashSHA-256（不可逆）认证比对：请求来的 Key 算 hash 查库，命中即通过——库内无明文也能验真
key_cipherSecretCipher（可逆）"小眼睛"按需解密展示/复制，单条解密接口取明文
key_prefix截断掩码列表只回前缀掩码，列表接口绝不返回密文/明文

约束：单 Agent ≤50 把；key_hash 全局唯一索引兜底；逻辑删除即认证失效；查看/删除强制校验 key.agentNum 与路径一致（防越权操作他人密钥）。

CASE 7-3　对外接口 Bearer 密钥认证（独立于 SSO 平面）

对外 4 个开放接口（/open/**）不走 SSO Cookie，而用 Authorization: Bearer ak-... 头认证，由独立的秘钥过滤器处理：取 Bearer Key → 算 SHA-256 → findByKeyHash 查库 → 命中且未删除则放行并绑定 Agent 身份。机机调用与人机登录态彻底分离，互不污染。

08文件存储安全 已实现

文件不经过后端中转，采用 OSS 预签名 URL（Presigned URL）方案：后端只签发短期有效的临时凭据，前端直传/直取 OSS。后端不持有文件字节，前端不持有 OSS 长期密钥，双向收敛泄露面。

演进项：若后续开放用户文件上传，需补齐类型白名单 + 大小限制 + 病毒扫描 + 独立 bucket 隔离（MVP 阶段 prompt 为纯文本，暂不支持上传）。

关键写操作发布领域事件（AGENT_CREATED / AGENT_VERSION_PUBLISHED / SKILL_SAVED / WORKSPACE_* 等，事件携带 operatorId 与时间戳）。认证侧由 infra/auth/audit/AuthAuditHelper.java 记录 LOGIN_SUCCESS / LOGIN_FAILED / ACCESS_DENIED / LOGOUT 四类事件，统一前缀 AUTH_AUDIT，并与请求 trace_id 贯通，可在 ELK/SLS 检索关联。

演进项：审计当前以结构化日志承载，规划接入审计表落库（append-only），保留期 1 年（待安全合规确认）。A2A 同步历史表 a2a_sync_history 已是无 deleted 字段的 append-only 审计表。

10.1 CORS 跨域白名单

adapter/config/CorsConfig.java：因使用 Cookie 携带凭证，allowCredentials=true，此时 origin 必须显式列举，禁用通配 *。生产环境必须在 application-prod.yml 覆盖为业务域名。

registry.addMapping("/**")
    .allowedOrigins(allowedOrigins.split(","))  // 显式白名单，不可为 *
    .allowedMethods("GET","POST","PUT","DELETE","OPTIONS")
    .exposedHeaders("X-Trace-Id")
    .allowCredentials(true).maxAge(3600);
