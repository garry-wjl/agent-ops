## 1. 背景与目标

### 1.1 现状

`rd-agent-be-infra/src/main/resources/db/migration/` 原有 `V1__init_agent.sql` ~ `V33__drop_uq_agent_ws_name.sql` 共 33 个增量脚本，含建表 DDL 与种子数据 DML。但项目**从未真正接入 Flyway**：

- 根 pom / infra pom 无 `flyway-core` / `flyway-mysql` 依赖；
- `application.yml` 无 `spring.flyway.*` 配置段；
- 库里无 `flyway_schema_history` 表。

历史迁移全靠手工 `docker exec mysql-test mysql ... < Vxx.sql` 逐个执行，常因"代码已引用新列、本地库未同步"导致运行时 `Unknown column` 报 500（详见 memory：[[project-rd-agent-be-db-no-flyway]]）。全新环境（CI / 新人本机 / 新部署库）无标准一键建库方式。

### 1.2 目标

系统首次上线、数据库结构已定版。以**测试环境数据库**作为标准，引入 Flyway 让后端**启动时自动执行迁移**，一次到位建全表 + 灌权限种子，开箱即用。

| 场景 | 期望行为 |
| --- | --- |
| 全新空库（prod 首次上线 / 新人本机 / CI） | `V1__init_schema_and_seed.sql` 全量执行，建 24 张表 + 权限种子，开箱即用 |
| 现有库（dev / stag 已有表，无 `flyway_schema_history`） | `baseline-on-migrate` 打基线到 `baseline-version=1`，V1 视为已应用跳过，仅执行 V2+ 增量 |
| 后续新增迁移 | 只需在 `db/migration/` 加 `V2__xxx.sql`，启动自动执行 |

### 1.3 非目标

- 不做历史 33 份脚本回填（已删除重做，不再保留）；
- 不做数据库类型切换（确认 MySQL）；
- 不引入 Liquibase 或自研 Runner 方案（方案评估见 §2）。

## 2. 方案选型

| 方案 | 做法 | 结论 |
| --- | --- | --- |
| **A. Flyway（采纳）** | 引依赖 + `spring.flyway.*` 配置 + 单份 V1 脚本 + baseline 兜底 | ✅ 开箱即用，长期维护成本最低 |
| B. 自研 ApplicationRunner | 仿 `PlatformAdminBootstrapper`，`JdbcTemplate` 读脚本 + 自维护版本表 | ❌ 重复造轮子，无 checksum 校验 / 事务回滚，仅作"不引依赖"退路 |
| C. Spring Boot `spring.sql.init` | `schema.sql`/`data.sql` + `mode=always` | ❌ 无版本追踪，每次启动全量重跑；需把脚本改全幂等，危险 |

**选 A。**

## 3. 实现方案

### 3.1 引入依赖

`rd-agent-be-infra/pom.xml` 新增两个依赖，版本由 `spring-boot-dependencies` BOM 统一管理（3.5.14 → flyway 11.7.2），不写 `<version>`：

```xml
<!-- Flyway 数据库迁移：版本由 spring-boot-dependencies BOM 管理（11.7.2）。
     flyway-core 提供 FlywayAutoConfiguration 装配基础；flyway-mysql 是 MySQL 方言驱动，
     缺它则 Flyway 识别不出 MySQL JDBC URL，启动报 "No database found to handle" -->
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-mysql</artifactId>
</dependency>
```

依赖位置说明：迁移脚本 `db/migration/` 物理上在 infra 模块，故依赖声明在 infra；adapter 作为启动模块通过 `adapter → application → infra` 传递链获得 flyway，运行时 classpath 完整（已 `dependency:tree` 验证 flyway-core / flyway-mysql 11.7.2 进入 adapter 传递树）。

### 3.2 配置

`rd-agent-be-adapter/src/main/resources/application.yml` 在 `spring.datasource` 之后新增 `spring.flyway` 段：

```yaml
spring:
  flyway:
    enabled: ${FLYWAY_ENABLED:true}
    locations: classpath:db/migration
    baseline-on-migrate: true
    baseline-version: ${FLYWAY_BASELINE_VERSION:1}
    validate-on-migrate: true
    clean-disabled: true
```

| 配置项 | 值 | 作用 |
| --- | --- | --- |
| `enabled` | `${FLYWAY_ENABLED:true}` | 默认全环境开启；可用环境变量紧急关闭 |
| `locations` | `classpath:db/migration` | infra 脚本编译后即在此 classpath 路径 |
| `baseline-on-migrate` | `true` | **核心**：现有非空库首次跑时不重放已存在结构 |
| `baseline-version` | `${FLYWAY_BASELINE_VERSION:1}` | 钉到当前仓库最大版本号 1；现有库 V1 视为已应用跳过，只跑 V2+。**必须随仓库实际最大版本号同步**，留高值会让后续增量被误判为"低于 baseline"而跳过 |
| `validate-on-migrate` | `true` | checksum 校验，防漂移 |
| `clean-disabled` | `true` | 生产安全，禁止 `flyway clean` 清库 |

**全环境统一开启，靠 baseline 兜底**，不在 prod 单独关闭。

### 3.3 单份 V1 脚本（核心变更）

删除全部 33 份历史脚本，重做单份：

- **路径**：`rd-agent-be-infra/src/main/resources/db/migration/V1__init_schema_and_seed.sql`（576 行）
- **数据来源**：测试环境 `rd_agent_be` 库（`rm-wz950hyg68l84xwz9.mysql.cn-shenzhen.rds.aliyuncs.com`）定版快照

**脚本结构：**

| 段 | 内容 |
| --- | --- |
| 头部 | `SET NAMES utf8mb4; SET FOREIGN_KEY_CHECKS=0;` + 说明注释 |
| DDL | 24 张 `CREATE TABLE`（agent / skill / skill_version / model / session / permission / role / role_permission / route_permission / workspace / user_workspace_role / agent_api_key / tool / prompt / sandbox / a2a_sync_history / message / evaluation 等） |
| 种子 DML | 5 张表 INSERT：`permission`(55)、`route_permission`(58)、`role`(4 内置角色)、`role_permission`(117)、`workspace`(仅 `WS-DEFAULT`，admin/member 清空成 `[]`) |
| 尾部 | `SET FOREIGN_KEY_CHECKS=1;` |

**4 个内置角色**：`RL-PLATFORM-ADMIN`（平台管理员）/ `RL-PLATFORM-USER`（平台普通用户）/ `RL-SPACE-ADMIN`（空间管理员）/ `RL-SPACE-MEMBER`（空间成员）。

**不含**：

- 业务运行时数据（agent / skill / model / session 等仅建空表）；
- `user_workspace_role`（随用户登录由应用层 `PlatformAdminBootstrapper` 写入，新环境登录后自动有平台管理员）；
- `flyway_schema_history`（Flyway 启动时自建）。

**对测试库历史污染的修正**（dump 时一并处理，避免把脏结构固化进标准脚本）：

1. **`agent` 表 comment 双重编码乱码**：测试库 metadata 里存的是 `åˆ›å»ºæ–¹å¼`（双重编码），非 dump 工具问题。修正为正常 UTF-8 `创建方式`（HEX 验证 `E5889B...`）。
2. **`skill` / `skill_version` 停在 V5 形态**：测试库没跑过 V9 收敛脚本，多 `skill_file_type` / `source_version` 列、`status` 默认 `DRAFT_ONLY`。对齐到与当前代码一致的干净结构（`status` 默认 `DRAFT`）。
3. **去噪**：剥离 dump 里的 `AUTO_INCREMENT=N`、`GTID_PURGED`、`SQL_LOG_BIN` 等环境相关噪音，保证脚本可移植。

### 3.4 baseline 机制行为推演

| 库状态 | `flyway_schema_history` | 启动行为 |
| --- | --- | --- |
| 空库（无表，prod 首次上线） | 不存在 | 不触发 baseline，V1 全量执行，建表 + 灌种子 |
| 现有库（有表，无 history，dev/stag） | 不存在 | 触发 baseline：插入 `version=1, type=BASELINE`；V1 视为已应用跳过；V2+ 执行 |
| 已接入后再次启动 | 存在 | 不再 baseline，仅执行未应用的 V2+ |

⚠️ **关键**：`baseline-version` 必须钉到**当前仓库最大版本号**。当前仓库只有 V1，故 `baseline-version=1`。若仍留 v1.0 文档里的 `33`，现有库 baseline 后会把 V2+ 当"低于 baseline"跳过 → 增量永远不执行。

### 3.5 各环境上线动作

| 环境 | 现状 | 上线动作 |
| --- | --- | --- |
| **prod** | 全新空库 | 直接启动，Flyway 全量跑 V1 建库灌种子。无需任何手工 DDL |
| **stag** | 已有表 + 测试数据 | 启动自动 baseline 到 v1，V1 跳过、结构不动、数据不丢；后续走 V2+ |
| **dev（本地）** | 各人库状态不一 | 建议 `DROP DATABASE rd_agent; CREATE DATABASE rd_agent;` 后启动，让 Flyway 全量重建为标准状态 |
| **CI** | 每次全新空库 | 自动全量跑 V1，无需特殊处理 |

### 3.6 无需手写代码

Spring Boot 检测到 classpath 有 `flyway-core` + 已配置 `DataSource`，自动装配 `FlywayAutoConfiguration`，在 MyBatis-Plus / 业务 bean 初始化前执行迁移。无需写任何 `@Configuration` 或 `ApplicationRunner`。

| 现象 | 原因 | 处理 |
| --- | --- | --- |

## 5. 风险与前置条件

### 5.1 现有库 schema 与 V1 一致性

`baseline-version=1` 的语义是"现有库已处于 V1 状态"。dev/stag 库若与单份 V1 脚本结构有出入（如旧库缺某列），baseline 后缺的部分不会补，仍可能 `Unknown column` 500。

**建议**：dev 库直接 `DROP DATABASE rd_agent; CREATE DATABASE rd_agent;` 后启动让 Flyway 全量重建；stag 若可接受，同样重建为标准状态最稳妥。

### 5.2 V1 脚本不可再改

接入后 V1 的 checksum 已记入 `flyway_schema_history`，任何对 V1 的改动都会触发 `validate` 失败。**后续 schema 变更一律走新增 `V2__xxx.sql`**，禁止改 V1。

### 5.3 多实例启动并发

K8s 多副本同时启动时，Flyway 默认用 `flyway_schema_history` 表的 `SELECT ... FOR UPDATE` 行锁串行化迁移，首个实例执行、其余等待后跳过，不会并发重复执行。无需额外配置。

### 5.4 与 MyBatis-Plus 的执行时序

Flyway 在 `InitializingBean` 阶段（Spring 容器初始化早期）执行，早于 MyBatis-Plus Mapper 扫描与业务 bean 初始化，保证业务跑 SQL 时表结构已就绪。无需调整启动类 `AgentBeApplication`。

### 5.5 prod 首次上线注意

prod 是全新空库，启动即全量跑 V1。务必确认：

- prod 库连接参数（`DB_HOST`/`DB_PORT`/`DB_USER`/`DB_PASSWORD`）已通过 K8s Secret / Apollo 注入；
- `FLYWAY_ENABLED` 未被显式关成 `false`；
- 首次部署后核对 `flyway_schema_history` 有 1 条 SUCCESS、权限种子表行数与本方案 §4.2 一致。

## 7. 后续约定

- 新增 schema 变更：在 `db/migration/` 加 `V{下一个版本号}__{英文描述}.sql`，脚本须幂等友好（`ADD COLUMN IF NOT EXISTS` / `INSERT IGNORE` 等），无需手工执行；
- 版本号严格递增，不复用、不跳号；当前下一版本号为 **V2**；
- 不再手动 `docker exec ... < Vxx.sql`（memory 中 [[project-rd-agent-be-db-no-flyway]] 的手工流程作废）；
- `baseline-version` 随仓库最大版本号同步上调（当前为 1，新增 V2 后无须改 baseline-version，因 baseline 只对"无 history 的现有库"首次生效）。
